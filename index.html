LECTURE 01

Business Intelligence Concepts

What Is Business Intelligence?

Business Intelligence (BI) is using tools and techniques to turn raw data into useful decisions. A simple way to think about it: data goes in, insight comes out, and a manager makes a better choice.

🧠 Analogy

Think of BI like a GPS for a business. Raw data (like road sensors and maps) is collected constantly. The GPS (BI system) processes all of it and tells you: "Turn left — there's traffic on the highway." You don't need to know how the GPS works internally; you just need the right output at the right time to make a decision.

The Analytical Hierarchy — 5 Levels

Analytics moves from simple "what happened" questions to complex "what should we do" questions.

Level Question It Answers Time Real Example
Descriptive What happened? Past "We sold 500 units in March."
Diagnostic Why did it happen? Past "Sales dropped because a competitor launched a cheaper product."
Predictive What will happen? Future "Based on trends, we'll sell 480 units next March."
Prescriptive What should we do about it? Future "Run a 10% discount campaign to push sales above 500."
Comparative How does X compare to Y? Any "Perth store vs Sydney store sales side by side."
💡 Quick Memory Trick

Think of it like a car accident:

  • Descriptive: "There was a crash on the freeway." (What?)
  • Diagnostic: "It happened because of wet roads and speeding." (Why?)
  • Predictive: "If it rains tonight, there's a 70% chance of another crash." (What next?)
  • Prescriptive: "Deploy speed cameras on wet roads to prevent it." (What to do?)
⚠️ Exam Trap

Predictive = "what WILL happen" (forecasting). Prescriptive = "what should we DO" (recommending action). Students often mix these two up. Predictive just tells you the future — prescriptive tells you how to change it.

Database Modelling

What Is a Database?

A database is organised, structured data stored consistently — like tables and lists, not free-form text. Think of it like a very powerful, shared spreadsheet that many people can use at once, with rules that keep the data valid.

🧠 Analogy — Library vs Pile of Books

A pile of books is data. A library is a database — books are catalogued, findable, categorised, and multiple people can use it simultaneously without chaos. A spreadsheet is like a personal bookshelf — fine for one person, but falls apart at scale.

Database vs Spreadsheet

Feature Spreadsheet Database
Multiple users at once ❌ One user at a time (usually) ✅ Many simultaneous users
Large data performance ❌ Slow with millions of rows ✅ Designed for scale
Access control ❌ Basic file permissions only ✅ Fine-grained (user A sees table X, user B sees table Y)
Ease of use ✅ Familiar, visual, easy ❌ Requires SQL knowledge

Entities and Attributes

📌 Key Definitions
  • Entity: A "thing" we want to store data about (a Person, a Product, a Transaction)
    • Attribute/Property: A characteristic of an entity (Person's Name, Product's Price)
  • Row / Record: One specific instance (one particular person, one specific product)
  • Column / Field: One attribute (the "Name" column, the "Price" column)

Relationship Cardinalities

Type Symbol Meaning Example
One to Many 1:M One parent, many children One Customer → many Invoices
Many to One M:1 Many children, one parent Many Invoices → one Customer
One to One 1:1 Each links to exactly one other One Person → one Passport
Many to Many M:M Both sides link to many Students ↔ Courses (a student takes many courses; a course has many students)
⚠️ Many-to-Many needs a linking table

You can't directly store a M:M relationship. You need a third "junction" table holding pairs of PKs. For Students ↔ Courses, you'd have an Enrolment table with (studentID, courseID) pairs.

Database Design Steps (Memorise These)

  1. Define the entities — what "things" do we need to store? (People, Products, Orders...)
  2. Determine the tables — each entity usually becomes one table
  3. Identify Primary and Foreign Keys — how do rows uniquely identify themselves? How do tables link?
  4. Describe relationship cardinalities — is it 1:M, M:M, 1:1?
  5. Define all attributes — what columns does each table need?

ACID Principles

🧠 Analogy — ATM Cash Withdrawal

You withdraw $100 from an ATM. ACID guarantees that EITHER both happen (your account is debited AND cash dispensed) OR neither does. The bank balance can never be reduced without you getting the cash.

  • Atomicity: The whole withdrawal succeeds or nothing changes (no partial results)
  • Consistency: The bank database stays valid — you can't have a negative balance unless rules allow it
  • Isolation: Two people withdrawing simultaneously get correct results, as if they went one at a time
  • Durability: Once confirmed, the transaction is permanent — even if the power cuts out

Use VARCHAR for names, descriptions, emails — anything variable length.
Use CHAR for fixed codes like Australian state codes (NSW, VIC, QLD — always 2–3 chars) or postcodes (always 4 digits).

Creating a Database & Table — Full Example

💡 Step-by-step — Building a Customer table from scratch
-- Step 1: Create a database (do this once)
CREATE DATABASE 12345678_db;

-- Step 2: Tell MySQL to use that database (run at start of every session)
USE 12345678_db;

-- Step 3: Create a Customer table
CREATE TABLE 12345678_db.Customer (
  id          INT          NOT NULL AUTO_INCREMENT,
  fullName    VARCHAR(100) NOT NULL,
  email       VARCHAR(255) NOT NULL,
  birthDate   DATE,          -- nullable: not everyone shares their DOB
  isActive    BOOLEAN      DEFAULT 1,
  PRIMARY KEY (id)
);

Reading this column by column: id is a whole number, always required, auto-assigned. fullName is text up to 100 chars, always required. birthDate is optional (nullable). isActive defaults to 1 (true) if not specified.

💡 Example — Changing the Customer table after it's created
-- Forgot to add a phone number column? Add it now:
ALTER TABLE Customer ADD COLUMN phoneNumber VARCHAR(20);

-- "fullName" is confusing — rename it to "customerName":
ALTER TABLE Customer RENAME COLUMN fullName TO customerName;

-- Change phone to be mandatory (add NOT NULL):

-- Oops, phone number column is wrong — remove it entirely:
ALTER TABLE Customer DROP COLUMN phoneNumber;

💡 UPDATE — Changing existing data
-- Alice changed her email — update just her row:
UPDATE Customer
SET email = 'alice.smith@newemail.com'

DELETE FROM Table without WHERE → every row gone. DROP TABLE → entire table and data gone. Always run a SELECT first to preview exactly which rows would be affected before deleting.

Running SQL Scripts

Instead of typing one command at a time, you write all your SQL in a .sql file and run the whole file at once. Commands run top-to-bottom. If one fails, everything stops at that line.

⚠️ Script Rules to Remember

  • Commands run instantly on the server — there's no "undo"
  • UniApps users: save scripts to OneDrive

Generated Columns

A generated column is calculated automatically from other columns. You never insert a value for it — the database works it out for you every time other values change.

🧠 Analogy

A spreadsheet formula like =B2*C2 in cell D2. You put values in B2 and C2, and D2 automatically shows the result. A generated column works the same way — you provide the ingredients (quantity, price), the database calculates the result (total).

💡 Example — TransactionItem with generated columns
CREATE TABLE TransactionItem (
  id          INT   NOT NULL AUTO_INCREMENT,
  description VARCHAR(255) NOT NULL,
  quantity    INT,
  unitPrice   FLOAT,
  hasGst      BOOLEAN    DEFAULT 0,
  totalPrice  FLOAT      GENERATED ALWAYS AS (unitPrice * quantity) STORED,
  taxAmount   FLOAT      GENERATED ALWAYS AS (hasGst * (unitPrice / 11)) STORED,
  PRIMARY KEY (id)
);

If you insert: description="Widget", quantity=5, unitPrice=20.00, hasGst=1

What MySQL stores (totalPrice and taxAmount auto-calculated)
id description quantity unitPrice hasGst totalPrice taxAmount
1 Widget 5 20.00 1 100.00 1.82

You never insert values for totalPrice or taxAmount — they're calculated. Use DEFAULT for them when inserting: INSERT INTO TransactionItem VALUES (DEFAULT, "Widget", 5, 20.00, 1, DEFAULT, DEFAULT);

DEFAULT and CHECK Constraints

💡 Example — Adding safety rules to a table
-- 1. DEFAULT: if hasGst is not supplied, assume 0 (no tax)
ALTER TABLE TransactionItem MODIFY COLUMN hasGst BOOLEAN DEFAULT 0;

-- 2. CHECK: quantity must always be positive (can't sell -3 widgets)
ALTER TABLE TransactionItem ADD CONSTRAINT qCheck CHECK (quantity > 0);

-- 3. CHECK: price must be positive too
ALTER TABLE TransactionItem ADD CONSTRAINT priceCheck CHECK (unitPrice > 0);

-- Now try to insert an invalid row:
INSERT INTO TransactionItem (description, quantity, unitPrice) VALUES
  ('Bad Item', -5, 10.00);
-- ❌ ERROR: Check constraint 'qCheck' is violated.

CHECK constraints act like bouncers — they reject any data that breaks the rules before it enters the table.

Foreign Keys — Linking Tables

⚠️ Golden Rule

The parent table (the one being referenced) must exist first. You can't create a FK pointing to a table that doesn't exist yet. Create TransactionItem before Transaction if Transaction references TransactionItem.

💡 Example — Invoice references Customer
-- Create Customer FIRST (it's the parent)
CREATE TABLE Customer (
  id       INT          NOT NULL AUTO_INCREMENT,
  name     VARCHAR(100) NOT NULL,
  PRIMARY KEY (id)
);

-- THEN create Invoice (it's the child, references Customer)
CREATE TABLE Invoice (
  id         INT   NOT NULL AUTO_INCREMENT,
  customerID INT,
  amount     FLOAT,
  PRIMARY KEY (id),
  CONSTRAINT fk_cust FOREIGN KEY (customerID)
    REFERENCES Customer(id)
    ON DELETE CASCADE
);

Now if you try to insert an Invoice with customerID=99 but Customer id=99 doesn't exist — the database rejects it. This is referential integrity.

Referential Actions — What Happens When a Parent Row Is Deleted?

Action Effect Best Used When…
CASCADE Also deletes the child rows automatically Child rows are meaningless without the parent (e.g. delete order → delete order items)
SET NULL Sets FK column to NULL in child rows Child can still exist, just "unlinked" (e.g. delete employee → invoices stay, just have no assigned employee)
RESTRICT Blocks the deletion of the parent if children exist You must not delete a Customer who has active Invoices
💡 CASCADE vs RESTRICT — Which to choose?

Scenario: You want to delete Customer "Alice Smith" who has 3 Invoices.

  • CASCADE: Alice is deleted → her 3 invoices are also deleted automatically. ✅ Good if invoices are meaningless without a customer. ❌ Bad if you need to keep financial records.
  • RESTRICT: MySQL blocks the deletion and says "can't delete Alice, she has invoices." You must delete the invoices first. ✅ Good for protecting important financial data.

Indexes

🧠 Analogy — Book Index

Without an index, finding "chapter about cats" in a 500-page book means reading every page. With a book index, you flip to "Cats — page 247" instantly. Database indexes work the same way — they let MySQL jump directly to matching rows instead of scanning the entire table.

💡 Example — Adding an index to speed up email lookups
-- Users log in via email — this column gets searched constantly.
-- Adding an index makes those lookups much faster:
CREATE UNIQUE INDEX idx_email ON Customer(email);

-- Remove the index (doesn't affect the data or table):
DROP INDEX idx_email;

Trade-off: Indexes speed up reads but use extra storage and slightly slow down writes (INSERT/UPDATE) because the index must be updated too.

GROUP BY — Grouping & Summarising

🧠 Analogy — Sorting a pile of receipts

Imagine you have 100 receipts from different shops. You sort them into piles by shop name. Now for each pile (group), you can ask: "How many receipts in this pile?" (COUNT) or "What was the biggest purchase?" (MAX). That's exactly what GROUP BY does — it makes the piles, and aggregate functions answer questions about each pile.

SELECT → FROM → WHERE → GROUP BY → ORDER BY Mandatory order — getting this wrong = syntax error. WHERE always before GROUP BY. GROUP BY always before ORDER BY.
⚠️ The Most Important Rule in GROUP BY

In a GROUP BY query, your SELECT list may only contain:

  1. Columns listed in the GROUP BY clause
  2. Aggregate functions (AVG, MIN, MAX, SUM, COUNT)

Why? When 10 rows collapse into one group, any non-grouped column could have 10 different values — MySQL doesn't know which one to show, so it errors.

The 5 Aggregate Functions

💡 All 5 functions demonstrated on the TransactionItem table

Assume this is the TransactionItem table:

TransactionItem — source data
id description quantity unitPrice hasGst
1 Laptop 2 899.00 1
2 Mouse 5 25.00 0
3 Keyboard 3 75.00 0
4 Monitor 1 450.00 1 
SELECT
  hasGst,
  COUNT(id)        AS numItems,
  AVG(unitPrice)   AS avgPrice,
  MIN(unitPrice)   AS cheapest,
  MAX(unitPrice)   AS mostExpensive,
  SUM(unitPrice)   AS totalPrice
FROM TransactionItem
GROUP BY hasGst;
Result — one row per hasGst group
hasGst numItems avgPrice cheapest mostExpensive totalPrice
0 (no tax) 2 50.00 25.00 75.00 100.00
1 (has tax) 2 674.50 450.00 899.00 1349.00

The group hasGst=0 contains Mouse ($25) and Keyboard ($75). The group hasGst=1 contains Laptop ($899) and Monitor ($450). Notice hasGst appears in both SELECT and GROUP BY — so you can tell which result row belongs to which group.

⚠️ NULL Behaviour in Aggregation

All aggregate functions skip NULL values. Example: if a column has values [10, NULL, 20, NULL, 30], then:

  • COUNT(col) = 3 (counts only non-NULL)
  • COUNT(*) = 5 (counts all rows including NULLs)
  • SUM(col) = 60 (adds only the non-NULL values)
  • AVG(col) = 20 (60 ÷ 3, not 60 ÷ 5)

This can significantly affect your results when data has missing values!

Date Functions in Grouping

💡 Example — Sales grouped by month and year

Without date functions, grouping by date gives one group per exact date (too granular). Date functions let you group by just the month or year.

-- Count how many transactions happened in each month of each year
SELECT
  YEAR(date)  AS year,
  MONTH(date) AS month,
  COUNT(id)   AS numTransactions
FROM Transaction
GROUP BY YEAR(date), MONTH(date)
ORDER BY YEAR(date) ASC, MONTH(date) ASC;
Result
year month numTransactions
2022 1 1
2022 4 1
2023 4 1
2023 7 1

Full Complex Query — All Clauses Together

💡 The Lecture's Most Complex Example — Broken Down
SELECT
  department,
  MONTH(date),
  YEAR(date),
  COUNT(id)        AS numSales,
  MIN(salePrice)   AS cheapestSale
FROM ExampleTable
WHERE department LIKE 'SALES %'
GROUP BY department, MONTH(date), YEAR(date)
ORDER BY MIN(salePrice) DESC;

Step by step — what MySQL does internally:

  1. FROM ExampleTable — load all rows from the table
  2. WHERE department LIKE 'SALES %' — filter: only keep rows where department starts with "SALES ". This happens BEFORE grouping.
  3. GROUP BY department, MONTH(date), YEAR(date) — group remaining rows. Every unique combination of (department, month, year) becomes one result row. If SALES-NORTH sold in Jan 2023 and Feb 2023, those are two separate groups.
  4. SELECT — calculate aggregates for each group: COUNT(id) = how many sales, MIN(salePrice) = cheapest sale price in that group.
  5. ORDER BY MIN(salePrice) DESC — sort the result groups: the group with the highest minimum sale price appears first.

AS Aliases, WITH ROLLUP

💡 WITH ROLLUP — Adding a grand total row
SELECT YEAR(date) AS yr, SUM(amount) AS totalSales
FROM Invoice
GROUP BY YEAR(date) WITH ROLLUP;
Result — note the NULL row at the bottom = grand total
yr totalSales
2022 $5,200.00
2023 $8,750.00
NULL $13,950.00 ← grand total for ALL years

The NULL in the yr column of the last row means "this is not one specific year — this is ALL years combined." It's the grand total row added by WITH ROLLUP.

LECTURE 06

Advanced Databases — Joins, Views, Spatial & Loading Data

Why Do We Need JOINs?

We already know that Foreign Keys create links between tables. But when you run a SELECT on one table, you only get that table's columns — you can't automatically see the related data from the other table. A JOIN solves this: it combines two tables into a single result based on matching column values.

🧠 Analogy — Two spreadsheet sheets

Imagine Sheet 1 has your customer list (id, name) and Sheet 2 has your invoice list (id, customerID, amount). To see "which customer paid what", you'd manually look up each customer by ID across both sheets. A JOIN does that lookup automatically and merges the two sheets into one combined view — like Excel's VLOOKUP, but for entire tables.

The Three Types of JOINs

The type of JOIN you use depends on which rows you want to keep when there is no match in the other table.

JOIN Type Rows Kept When to Use
INNER JOIN Only rows that have a match in both tables Most common — you only want complete matches (e.g. customers who have at least one invoice)
LEFT JOIN All rows from the left table + matching rows from the right (NULLs where no match) You want every row from the first table, even if it has no related data in the second (e.g. all customers, even those with no invoices)
RIGHT JOIN All rows from the right table + matching rows from the left (NULLs where no match) You want every row from the second table regardless of whether it has a match in the first

The Venn Diagram Explained

The slide shows three Venn diagrams with circles A (left table) and B (right table). The shaded (blue) area is what gets returned:

  • LEFT JOIN: All of circle A is blue (all left rows kept) plus the overlapping intersection
  • INNER JOIN: Only the intersection (overlap) is blue — only matched rows from both
  • RIGHT JOIN: All of circle B is blue (all right rows kept) plus the intersection
📌 Key Syntax
SELECT * FROM TableA INNER JOIN TableB ON TableA.TheID = TableB.TheID;
-- Replace INNER JOIN with LEFT JOIN or RIGHT JOIN as needed
-- The ON clause specifies which columns to match between the two tables

Key points about JOIN syntax:

  • The ON keyword specifies the matching condition — usually a FK = PK
  • You can technically join on any two columns with matching values, not just FK relationships
  • Rarely can you use SELECT * in a JOIN — both tables may have columns with the same name (e.g. both have id), causing confusion. Specify which columns you want with table prefixes.
  • Use AS to rename conflicting column names in the output

⚠️ Exam Traps — JOINs
  • INNER JOIN is the most commonly used — when in doubt, this is usually what's needed.
  • LEFT/RIGHT is about which table you keep ALL rows from, not about which direction you read the query. LEFT = keep all of the first (left) table.
  • Non-matching rows show NULL in columns from the other table — not zero, not blank, NULL.
  • Always prefix column names with the table name when both tables share column names (e.g. both have id): write Customer.id, not just id.
  • UNION (combining all rows from both tables) is briefly mentioned but not required for this unit.

Views — Virtual Tables

A view is a saved SELECT query that acts like a table. You give it a name, and from then on you can query it just like any regular table — but it's not storing new data, it's just re-running the SELECT every time you access it.

🧠 Analogy — A saved filter in Excel

In Excel, you can save a filtered view of your data so colleagues can open it and always see the filtered result without needing to know the filter settings. A database view works the same way — the complex query is hidden inside the view, and users just run SELECT * FROM ViewName to get the result.

📌 View Syntax
-- Create a view
CREATE VIEW <ViewName> AS SELECT ...;

-- Update (replace) an existing view
CREATE OR REPLACE VIEW <ViewName> AS SELECT ...;

-- Delete a view
DROP VIEW <ViewName>;

-- Inspect a view's definition (like SHOW CREATE TABLE)
SHOW CREATE VIEW <ViewName>;

-- Query a view exactly like a table
SELECT * FROM <ViewName>;
💡 Three valid view examples (from the lecture)
-- 1. Simple view: all columns from one table
CREATE VIEW ExampleView AS
  SELECT * FROM ExampleTable;

-- 2. Filtered view: only one column
CREATE VIEW ExampleViewTwo AS
  SELECT AttributeOne FROM ExampleTable;

-- 3. Complex view: aggregation, WHERE, GROUP BY, ORDER BY
CREATE VIEW ExampleViewThree AS
  SELECT AttributeThree, MAX(AttributeTwo)
  FROM ExampleTable
  WHERE AttributeThree < 9000
  GROUP BY AttributeThree
  ORDER BY AttributeThree DESC;

After creating these, you can query any of them exactly like a table: SELECT * FROM ExampleViewThree;

💡 Real-world view — Hiding JOIN complexity
-- Create a view that always shows invoices with customer names
CREATE VIEW InvoiceDetails AS
  SELECT
    Invoice.id        AS invoiceID,
    Customer.fullName AS customerName,
    Invoice.amount,
    Invoice.date
  FROM Invoice
  INNER JOIN Customer ON Invoice.customerID = Customer.id;

-- Now anyone can get invoice + customer data with a simple query:
SELECT * FROM InvoiceDetails WHERE amount > 100;

The complex JOIN is hidden inside the view. Users just query InvoiceDetails like a normal table — they don't need to know how to write the JOIN themselves.

📌 Views vs Generated Columns — The connection

The lecturer draws a parallel: generated columns compute values for individual cells on-the-fly (VIRTUAL) or store them (STORED). Views apply the same idea to an entire table — the result of a SELECT query can be treated as a table, computed fresh each time you query it.

⚠️ Exam Trap

A view does not store new data — it re-runs its underlying SELECT query every time you access it. Think of it as a shortcut to a query, not a copy of data. The exception would be a materialised view (not covered in this unit).

Spatial Databases — Storing Location Data

Spatial data adds real-world location to database rows — letting you store where something physically is and run queries like "find all stores within 10km of me."

📌 Key Terms
  • Longitude: The east-west position — think "along" the horizontal axis. Perth is approximately 115.86°E.
  • Latitude: The north-south position — the "other one." Perth is approximately -31.95° (south).
  • Point: A single location (longitude, latitude pair) — most common spatial type in this course.
  • Line: A series of connected points (e.g. a road).
  • Polygon: A closed shape (e.g. a suburb boundary, a building footprint).
⚠️ Important — Longitude comes FIRST in MySQL

MySQL's spatial format uses POINT(longitude latitude) — longitude first, latitude second. This is the opposite of how most people say it ("lat, long"). Get this wrong and your points will be in the wrong location (or even invalid).

💡 Creating and inserting spatial point data
-- Create a table with a POINT column for storing locations
CREATE TABLE Locations (
  id       INT   NOT NULL AUTO_INCREMENT,
  name     VARCHAR(100),
  position POINT,
  PRIMARY KEY (id)
);

-- Insert UWA's location: Long=115.8174, Lat=-31.9796
INSERT INTO Locations (name, position) VALUES
  ('UWA Business School', ST_GeomFromText('POINT(115.8174 -31.9796)')),
  ('Perth CBD',           ST_GeomFromText('POINT(115.8605 -31.9505)')),
  ('Fremantle',           ST_GeomFromText('POINT(115.7500 -32.0569)'));
💡 Viewing spatial data — use ST_AsText()
-- Without ST_AsText: MySQL shows garbled binary characters for POINT columns
SELECT name, position FROM Locations;
-- ❌ position column shows: ??????? (unreadable binary)

-- With ST_AsText: readable text format
SELECT name, ST_AsText(position) AS location FROM Locations;
Result — readable coordinates
name location
UWA Business School POINT(115.8174 -31.9796)
Perth CBD POINT(115.8605 -31.9505)
Fremantle POINT(115.7500 -32.0569)

Always use ST_AsText() when SELECTing a geometry/point column — otherwise MySQL returns unreadable binary characters.

💡 Spatial query — Find locations within 10km of a point
-- Find all locations within 10 kilometres of Perth CBD
SELECT name, ST_AsText(position)
FROM Locations
WHERE ST_Distance_Sphere(position, ST_GeomFromText('POINT(115.8605 -31.9505)'))
  <= 10 * 1000   -- 10km converted to metres (ST_Distance_Sphere returns metres)
ORDER BY name;

Breaking this down:

  • ST_Distance_Sphere(pointA, pointB) — calculates the distance in metres between two points on Earth's surface
  • 10 * 1000 — converts 10 kilometres to 10,000 metres (the function uses metres)
  • The result only includes rows where the distance is ≤ 10,000m from Perth CBD
⚠️ Spatial Exam Traps
  • ST_GeomFromText('POINT(long lat)') — longitude first, latitude second (opposite to how we normally say it)
  • ST_Distance_Sphere returns metres, not kilometres — multiply km by 1000
  • Always wrap geometry columns in ST_AsText() when using SELECT — without it, the output is unreadable binary

How BI Tools Work — The General Workflow

All modern BI tools follow the same basic workflow, regardless of which software you use:

  1. Connect to data — import from Excel files, live databases (like MySQL), online APIs, or other sources. Can be a one-time snapshot or a live/real-time connection.

DAX Language — Writing Calculations

DAX (Data Analysis Expressions) is the formula language used in Power BI. It's similar to Excel formulas — if you know Excel, DAX will feel familiar. DAX lets you create two things:

DAX Object What It Is Example

💡 DAX syntax — how it works
-- DAX Measure: Total Units Sold
Total Units Sold = SUM(financials[Units Sold])

-- DAX Measure: Gross Total Revenue
GrossTotal = SUM(financials[Gross Sales])

-- DAX Table: Create a Calendar table spanning 2013–2014
Calendar = CALENDAR(DATE(2013,01,01), DATE(2014,12,31))

Breaking down the syntax: MeasureName = FUNCTION(TableName[ColumnName])

  • financials = the table name (from your loaded data)
  • [Gross Sales] = the column name in square brackets
  • SUM(...) = the DAX function (same as Excel's SUM)
  • The measure name is on the left of the =

Dummy Variables — Data Cleaning Concept

A dummy variable (also called a binary indicator) converts a categorical column into one or more True/False (1/0) columns — one per category value. This is needed for certain statistical analyses like correlation.

💡 Example — Converting a categorical column to dummy variables

Suppose you have a Transmission column with values: "Manual" and "Automatic".

Before — one categorical column
Car Transmission
Car A Manual
Car B Automatic
Car C Manual
After — dummy variable (only X−1 = 1 column needed)
Car isManual
Car A 1 (True)
Car B 0 (False → means Automatic)
Car C 1 (True)

Why only X−1 columns? Because if you know "isManual = 0", you already know it's Automatic — a second "isAutomatic" column would be redundant (always the opposite). The "all False" case implicitly represents the omitted category.

⚠️ Correlation with Binary/Dummy Variables

Correlation with binary (0/1) variables is statistically limited — because the variable has almost no variability (only two values: 0 or 1), the correlation coefficient can be misleading. The lecturer says: for binary variables, a bar chart comparing the two groups is usually more meaningful than a correlation coefficient.

  • Big data limits: Querying huge datasets in real-time is slow — you may need to pre-process or limit query sizes

📌 Why Polygons are Most Useful for Analysis

Polygons have area — this means you can calculate how much of one region overlaps with another, whether a point falls inside a region, and how to colour entire regions by a data value (choropleth maps). Points and lines lack this richness.

Spatial Operations You Can Do

Topological Operations

  • Intersection: Do two areas overlap? By how much?
  • Contains / Within: Is point A inside polygon B?
  • Disjoint: Are two shapes completely separate?
  • Distance: How far is point A from polygon B?
  • Touching: Do two shapes share a boundary edge?

Spatial Joins

  • Point-in-polygon: Which stores (points) fall within which country (polygon)? — like a database JOIN but based on physical location rather than a matching ID
  • Proximity: Which points are near each other and might represent the same real-world thing?
💡 Example — Spatial join in practice

You have a table of 500 coffee shop locations (points) and a table of suburbs (polygons). A spatial join tells you: "Which suburb does each coffee shop fall in?" — linking each point to its containing polygon automatically, based on geography, not on a shared ID column.

Advanced Spatial in Power BI — Choropleth Maps

A choropleth map (also called a "filled map") shades regions (polygons) with different colours based on a data value. Darker shade = higher value, lighter = lower, for example.

💡 Bubble map vs Choropleth map — comparison
Bubble Map (L7)
  • Circle placed at a coordinate
  • Circle size represents the value
  • Problem: large countries get big circles just due to geography — misleading
  • Good for point data (individual locations)
Choropleth / Filled Map (L8)
  • Entire country/region is coloured
  • Colour shade/intensity represents the value
  • Easier to compare countries visually at a glance
  • Requires polygon boundary data for each region

Important Considerations for Choropleth Maps

⚠️ Map Design Pitfalls — Exam Important
  • Colour scale matters: Choose a colour scheme that makes differences clearly visible. A scale that goes from pale yellow to mid-grey is hard to interpret — you want a perceptually uniform scale.
  • Don't misrepresent: Just like bubble maps where big circles can be misleading, a choropleth can be misleading if large-area countries dominate the eye even with small values (e.g. Russia looks dominant just because it's geographically huge).
  • Colour blindness: Consider users who cannot distinguish red from green. Use colour-blind-safe palettes (e.g. blue-to-orange rather than red-to-green).
  • Context matters: Always label your map, include a legend, and consider what your audience will assume about the colours.

Data Workflows, Visualisation Theory & MECE

What Is a Data Workflow?

A data workflow is a sequence of tasks carried out to process data and turn it into something useful — a report, a dashboard, a prediction. Different projects have different workflows, but at a high level every BI project shares the same five-stage pipeline.

🧠 Analogy — A restaurant meal

A restaurant meal follows the same high-level steps regardless of what's on the menu: identify what the customer wants (problem identification), source the ingredients (data acquisition), prepare them in the kitchen (data preparation), cook the dish (data analysis), plate and serve it (visualisation & reporting). The ingredients and cooking style change; the pipeline stays the same.

The 5-Stage BI Workflow (Memorise This)

Problem Identification → Data Acquisition → Data Preparation → Data Analysis → Visualisation & Reporting ⚠️ The majority of time is spent in the first THREE stages — not in the analysis or reporting!
⚠️ Exam Trap — Where the time really goes

Students assume most time is spent on analysis or building beautiful dashboards. The lecture explicitly states: "the majority of time is spent in the first three steps" — Problem Identification, Data Acquisition, and Data Preparation. Real-world data is messy and incomplete. Getting it ready takes most of the effort.

Stage 1 — Problem Identification

Before touching any data, define exactly what question you are trying to answer and who will use the output. Without this, you risk wasting time building something nobody needs, or analysing the wrong data entirely.

📌 What a Good Problem Statement Contains
  • What question are you answering?
  • Who will use the dashboard/report?
  • Both of these may change during the project — that's OK, but keep revisiting them.
💡 Example from the lecture — A well-formed problem statement

"I am interested in the average daily percentage change of the stock prices of Microsoft, Apple and Amazon."

From this single sentence you can already determine:

  • Data needed: Daily stock prices for MSFT, AAPL, AMZN
  • Analysis needed: Percentage change day-on-day, then average
  • Visualisation: Likely a time-series line chart, one line per company

A vague problem statement like "I want a stock dashboard" gives you none of this direction.

Stage 2 — Data Acquisition

Finding and obtaining the right data. This has two layers: theoretical issues (is this the right data?) and practical issues (can I actually get it?).

Theoretical Issues — Evaluating a Data Source

Question to Ask Why It Matters
Is the source trustworthy and authoritative? Data from an unverified source may be wrong, biased, or fabricated
Is there metadata (a description of the data)? Without metadata you may not know what columns mean or how values were measured
Does it conform to a recognised standard? Standardised formats (e.g. ISO date formats) are easier to integrate with other data
Does it actually answer the problem? It must be relevant — nearby data isn't good enough if it doesn't directly address the question
Are there licensing issues? Some data costs money, has time restrictions, or has legal limits on how it can be used
Is the data current? Historical data is fine for historical questions, but wrong for real-time decisions
How accurate is it? Data collected with poor instruments or biased sampling gives unreliable results
How is it recorded? (e.g. time series frequency) Hourly vs daily vs monthly data will produce very different analyses
What format is it in? Does it work with your tools? (CSV, JSON, API, proprietary format?)
Imported or connected? Determines whether the data stays fresh or becomes a snapshot

Practical Issues — Actually Getting the Data

  • File size: Can the file be sent over the internet at all? A 50GB dataset can't be emailed.
  • Transfer speed: How long will it take to download or stream?
  • Generation time: How long does it take for the data to be produced at the source? (e.g. a report that's generated overnight)

Stage 3 — Data Preparation

Real data almost never arrives in the perfect format. This stage fixes it. The lecture lists six common problems:

Problem What It Means Example Fix
Missing data Some cells/rows have no value Impute (fill in) with an average, or remove the row if critical
Wrong format A number stored as text, a date stored as a string Change data type in Power Query
Inconsistent values "Australia", "AUSTRALIA", "aus" all mean the same thing but are treated as different Standardise to UPPERCASE or a single canonical form
Needs normalisation Values are on wildly different scales (e.g. salary in thousands vs age in years) Normalise to 0–1 range or standardise (z-score)
Needs enrichment The dataset is incomplete — it needs extra data joined from another source JOIN with a lookup table to add country names to country codes
Irrelevant data Columns or rows that have nothing to do with the problem Remove columns, filter out rows (e.g. de-select "Montana" product)
📌 ETL — Extract, Transform, Load

ETL is a 50-year-old acronym widely used in data engineering that maps almost exactly onto Data Preparation:

  • Extract: Pull the data out of the source system (database, API, file)
  • Transform: Clean, reshape, and convert it to the format you need
  • Load: Put it into the destination system (your data model, warehouse, or Power BI)

ETL and data preparation are closely related but not identical — ETL is one method/approach to covering acquisition and preparation. They work together, especially with data warehouses.

Stage 4 — Data Analysis

This is where you actually answer your problem statement. In Power BI, analysis and visualisation are tightly integrated — you often build the visual and the analysis at the same time.

Exploratory Data Analysis (EDA)

Before diving into deep analysis, always start with EDA — quick descriptive statistics and simple visualisations to understand what the data looks like, spot anomalies, and form hypotheses.

The 11 Analysis Activity Types (Memorise These)

Get Value What is a single specific value? "What was BHP's closing price today?"
Filter Which rows meet a condition? "Which products sold more than 500 units?"
Derive Value Compute a new value from existing ones "What is the average click-through rate of each ad?"
Find Extreme What is the maximum or minimum? "Which salesperson sold the most?" (MAX)

The MECE Principle

MECE stands for Mutually Exclusive, Collectively Exhaustive. Developed by McKinsey, it's a framework for breaking complex problems into smaller, clean sub-problems without overlap or gaps.

📌 MECE Defined
  • Mutually Exclusive: Each item belongs to exactly one category — no overlap. A sale can only belong to one product, one region, one month.
  • Collectively Exhaustive: All items together cover everything — no gaps. All 10 products' profits sum to the total profit — nothing is left out.
💡 MECE Example from the lecture — 10-product business

A company sells 10 products. It tracks profit and stock level per product.

  • Total profit = sum of each individual product's profit. Each product's profit is mutually exclusive (Product A's profit doesn't include Product B's). All 10 together are collectively exhaustive (they add up to 100% of total profit).
  • Total stock = sum of each product's stock level. Same logic — each product's stock is separate, and all together account for every unit in the warehouse.

Why it matters for BI: MECE enables drill-up/drill-down in dashboards. You can start at the total company level (collectively exhaustive), then drill into each product (mutually exclusive sub-problems) without any double-counting or missing items.

⚠️ Exam Trap — MECE and Slicers

The lecture mentions that for a slicer to work properly in Power BI, the data must be mutually exclusive. If the same customer appears in two categories (e.g. "Enterprise" and "Government"), clicking one slicer value would not correctly isolate data — you'd get overlap. MECE-compliant data structure is a prerequisite for meaningful interactive filtering.

Stage 5 — Visualisation & Reporting

The final stage: presenting your findings to your audience. Two major pitfalls to avoid:

⚠️ The Two Big Presentation Mistakes
  1. Confusing fact for opinion: The data should tell the story — not your personal interpretation imposed on top of it. Present what the data shows, not what you want it to show.
  2. Misrepresenting data: Selective representation (cherry-picking data points), misleading chart types, unusual or truncated axes, and poorly labelled charts all distort the viewer's understanding.

Examples of Bad Visualisation (Slide 22)

The lecture shows two real examples of misleading charts used by news channels:

💡 Bad Chart 1 — FOX News Pie Chart

A pie chart must sum to 100% — this chart makes each candidate look large simultaneously, which is mathematically impossible. The 3D perspective also distorts the slice sizes visually.

What's wrong: Wrong chart type for the data, values don't sum to 100%, 3D effect adds visual distortion, no context for what the percentages represent.

The bars' heights are clearly not proportional to the percentages — the "Not At All" bar (13%) appears taller than "Very" (34%). The Y-axis is non-zero-based or distorted.

Non-Relational Databases — MongoDB & Graph Databases

Quick Revision — Key Differences Between Database Types

Question Answer
Main difference: NoSQL vs Relational? NoSQL databases have no fixed schema — each record/document can have different fields. Relational databases require every row to share the same columns.
Main difference: Document DB vs Relational? Data is not stored in tables but in multiple queryable documents (like JSON objects), each of which is a record.
Is a document DB always NoSQL? Yes — in practice, document databases are NoSQL. But NoSQL is broader: not all NoSQL databases are document-based.
When to use a graph database? When the relationships between entities are the most important element — e.g. social networks, recommendation engines, fraud detection.

MongoDB — A Document (NoSQL) Database

MongoDB stores data as documents — JSON-like objects where each document can have completely different fields. Think of it as storing a filing cabinet of index cards where every card can have different information written on it.

🧠 Analogy — Excel vs Word documents

A relational database is like an Excel spreadsheet — every row has the same columns. MongoDB is like a folder of Word documents — each one can contain completely different content and structure. This flexibility is the main advantage of document databases.

📌 MongoDB Terminology vs MySQL
MySQL (Relational) MongoDB (Document)
Database Database
Table Collection
Row / Record Document
Column / Attribute Field

MongoDB CRUD Commands

💡 Creating a Collection and Inserting Documents
// Create a collection (equivalent to CREATE TABLE in MySQL)
db.createCollection("transactions")

// Insert one document (preferred: insertOne)
db.transactions.insertOne({
  id: 1,
  description: "Basic Widget",
  quantity: 1,
  unitPrice: 123.45,
  totalPrice: 123.45,
  hasGst: true
})

// Insert multiple documents at once (preferred: insertMany)
db.transactions.insertMany([
  { id: 2, description: "Advanced Widget", quantity: 5, unitPrice: 25.00, hasGst: false },
  { id: 3, description: "Premium Widget", quantity: 2, unitPrice: 75.00, hasGst: true  }
])

Notice: unlike MySQL, there's no schema — you don't define columns upfront. Each document can have different fields. hasGst: true is a real Boolean (not 0/1 like MySQL).

💡 Reading / Querying Documents — .find()
// Find ALL documents in a collection — use .pretty() for readable output
db.transactions.find().pretty()

// Find where id equals 1
db.transactions.find({ id: 1 })

// Find where unitPrice is less than 100
db.transactions.find({ unitPrice: { $lt: 100 } }).pretty()

// Find where hasGst is NOT false (i.e. has GST)
db.transactions.find({ hasGst: { $ne: false } }).pretty()

  • MongoDB uses $keywords (dollar sign prefix) for operators — $lt, $gt, $ne, $in
  • MySQL uses plain symbols: <, >, <>, IN
  • MongoDB uses .find(); MySQL uses SELECT ... WHERE
  • MongoDB uses .pretty() to format output readably — MySQL has no equivalent
  • MongoDB collections have no fixed schema — each document can have different fields

Graph Databases

A graph database is based on the mathematical concept of a graph — a structure made of nodes and edges.

📌 Key Terms
  • Node (also called vertex): an entity — like a Person, Movie, or Product. Nodes hold data (attributes).
  • Edge (also called relationship): a directed connection between two nodes with a meaning. Edges also hold data (e.g. the date of a relationship, its strength).
  • Crucially: both nodes AND edges hold data — this is different from relational databases where only rows (not their connections) hold data.
💡 Example — Marvel Movie Graph

Nodes: Person (Anthony Russo), Movie (Captain America: Winter Soldier), Character (Cap)

Edges: "Directed" (Russo → Movie), "Acted In" (Person → Movie), "Plays" (Person → Character)

-- Cypher query language (used by Neo4j)

-- Get everything
MATCH (n) WHERE n:Person OR n:Movie OR n:Character RETURN n

-- Get a specific movie
MATCH (m:Movie {name: "captain america winter"}) RETURN m

-- Find who directed via relationship traversal
MATCH m=(p:Person {name: "anthony russo"})-[r:Directed]->() RETURN m

Notice: graph queries can traverse relationships (-[r:Directed]->) — something that requires multiple JOINs in SQL.

LECTURE 11

Security, Ethics & Privacy

Why Data Is Sensitive

In the course of business, organisations collect vast amounts of data from customers and clients. Some of this data is required by law (e.g. Anti-Money Laundering / Counter-Terrorism Financing legislation requires identity verification). But data is a powerful asset — and once certain data is disclosed, it cannot be undisclosed.

📌 Key Properties of Data That Make It Risky
  • Immutability of some data: You can change your password, but you can't change your date of birth, passport number, or health history. Once leaked, personally identifying information (PII) can cause permanent harm.
  • Business data ownership: Unlike personal data, business data (trade secrets, IP) is technically "owned" and can be changed — but leaking it to competitors is still devastating.
  • Not "owned" by anyone: Data about a person exists in a legal grey area — the person it describes doesn't technically own it in many jurisdictions.

Security Issues — Preventing Leaks

An unprotected system can leak data — providing it to people who shouldn't have access. Four key preventions:

Prevention What It Means Why It Matters
Strong authentication Use strong, unique usernames and passwords — or better, multi-factor authentication Weak passwords are the most common entry point for attackers
Minimal permissions Each user/group gets only the permissions they need — nothing more If an account is compromised, the attacker can only access what that account can — limiting damage
Keep software updated Apply patches and security updates promptly Most breaches exploit known vulnerabilities that have already been patched — unpatched systems are sitting targets
Audit logs Enable detailed logs of who accessed what and when "Prevention is better than cure, but being able to do a post-mortem is better than nothing" — if a breach occurs, logs tell you what happened

Ethical Issues — Misusing Data You Legally Hold

Even if data is legally collected, using it in ways the person didn't consent to is unethical. Examples:

Issue Example Why It's Problematic
Targeted advertising Using purchase history to serve targeted ads without explicit consent A form of surveillance — the person may not realise their behaviour is being tracked and monetised
Health outcome prediction Insurance company using personal data to predict illness risk and adjust premiums Discriminates based on data the person may not have knowingly provided for that purpose
Algorithmic bias AI system predicts job performance using historical data that embeds existing biases (e.g. gender bias in hiring) Creates "digital stereotypes" — automated discrimination at scale
Selling to third parties Data collected for one purpose sold to another company without consent Breaks the implicit or explicit agreement about how data will be used
Email list sign-ups Auto-subscribing someone to a mailing list when they provide an email for a receipt Anti-spam laws exist but are inconsistently enforced globally

Privacy Issues

Privacy is about ensuring that personal data is only accessible to those who need it, only for the purposes agreed upon.

  • Organisations should collect only the minimum data necessary — not everything they can get
  • Disclosure of private data can lead to fraud, embarrassment, or reputational damage
  • Both technical controls (encryption, access control, audit logs) AND social controls (training, culture, policy) are needed
  • These principles apply B2C and B2B — business intellectual property and trade secrets are also targets of corporate espionage

Case Studies — Real-World Examples

The lecture presents four case studies. For each, consider: What happened? Who was affected? What type of issue is it? How could it be prevented? Can it be remediated?

💡 Case 1 — Myki Data Leak (Victoria, Australia)

What happened: The Victorian Government released detailed Myki (public transport card) transaction data as part of a hackathon. Researchers cross-referenced this with publicly available tweets to identify politicians' card numbers and reconstruct their travel patterns.

Issues: Privacy (data re-identification), Ethics (data used beyond original purpose), Security (insufficient anonymisation before release).

Prevention: Proper anonymisation/aggregation before release; restrict granularity (zone-level, not stop-level); data governance review before publication.

⚠️ Key Lesson

Anonymised data can be re-identified when combined with other publicly available datasets. Data that seems safe in isolation may not be safe when combined.

💡 Case 2 — Mailing List Without Consent

What happened: Jim purchased a product online and provided his email to receive a receipt. The company added him to their marketing mailing list without asking for consent.

Issues: Ethics (using data beyond consented purpose), Privacy (email used without permission for marketing), potentially Legal (anti-spam laws like Australia's Spam Act 2003).

Prevention: Explicit opt-in checkboxes for marketing; keep receipt email separate from marketing consent.

💡 Case 3 — Optus "Hack" (Australia, 2022)

What happened: Optus exposed personal details (including passport and driving licence numbers) of up to 9.8 million customers through an unauthenticated API endpoint — no login or credentials required to retrieve customer data.

Issues: Security (no authentication on a sensitive endpoint), Privacy (highly sensitive PII exposed), Legal (regulatory/notification obligations).

Prevention: Require authentication on all API endpoints; penetration test APIs; apply principle of minimal permissions; don't store more sensitive data than necessary.

⚠️ Key Lesson

APIs must be secured. An unauthenticated endpoint exposing sensitive data is a critical vulnerability. This is exactly what "minimal permissions" and "keep software updated" protects against.

💡 Case 4 — AI Bias in Job Applications

What happened: An AI system ranked job applications based on patterns from existing employees. Jane's application was rejected despite being well-qualified — the algorithm learned that gender was a predictor of success because the existing workforce was predominantly male.

Issues: Ethics (algorithmic bias, discrimination), Privacy (personal attributes used for decisions without consent), Legal (potential discrimination law violations).

Prevention: Audit training data for bias before use; test AI systems for discriminatory outcomes; require human review of AI decisions; don't use protected attributes as model features.

⚠️ Key Lesson

AI inherits the biases in its training data. "Garbage in, garbage out" — biased historical data produces biased automated decisions at scale.

⚠️ The Three Categories — Know These Distinctly
  • Security: Protecting data from unauthorised access — technical controls, authentication, patching, audit logs
  • Ethics: Using data appropriately — consent, purpose limitation, avoiding discrimination and surveillance
  • Privacy: Ensuring data is only visible to those who need it — minimum data collection, access controls, preventing re-identification

These three often overlap in real cases — the Optus breach is primarily Security but also Privacy and has Legal implications. A case can involve all three simultaneously.

The Future of Databases & Revision

Blockchain — A New Kind of Database

Blockchain is described as a distributed, immutable ledger of transactions. Each word in that definition matters:

📌 Three Key Properties of Blockchain
Property What It Means Why It Matters
Distributed The "source of truth" is stored simultaneously across many machines (nodes) — there is no single central server No single point of failure; no single party controls or can alter the record unilaterally
Immutable Past transactions/records cannot be changed or deleted once written Creates a tamper-proof audit trail — ideal for financial transactions, contracts, and provenance tracking
Ledger of Transactions Stores a list of standardised operations (e.g. "Alice paid Bob $100") rather than arbitrary data Each entry is a discrete, verifiable event — not just a data record
🧠 Analogy — A shared document that can never be edited

Imagine a document shared with thousands of people simultaneously. Everyone can see the same content, and it records a history of every change. Now imagine that nobody — not even the platform — can edit or delete previous entries. That's blockchain. Multiple parties hold the truth simultaneously, and history is permanent.

Blockchain Use Cases

Use Case Why Blockchain Fits
Cryptocurrency (Bitcoin, Ethereum) Decentralised currency — no central bank needed; immutable transaction history prevents double-spending
NFTs (Non-Fungible Tokens) Prove ownership and provenance of digital assets without a central authority
Smart Contracts Self-executing contracts stored on the blockchain — automatically trigger when conditions are met, no intermediary needed
Supply chain tracking Immutably record every step a product takes — from factory to consumer; prevents fraud
💡 Key Exam Point — When to Use Blockchain

Good blockchain use cases are those where the distributed + immutable properties solve a problem that other systems cannot. If a traditional centralised database would work just as well, blockchain adds unnecessary complexity. Always ask: "Do we actually need this to be distributed and tamper-proof?"

Databases and Business Decision Making

The lecture revisits the core relationship between databases and BI:

  • Databases + BI tools together allow organisations to analyse data at scale
  • This enables: running more efficiently, making better decisions, reacting quickly (agility), and scaling faster
  • Data must be accessible, consistent, and fast — otherwise analysis takes too long and insights are out of date by the time they're ready. Hence, the DBMS used must be performant.
  • Volumes of data continue to grow exponentially — driven by IoT, social media, e-commerce, and sensors. The question of "where do we go next?" points to Web 3.0 and beyond.
