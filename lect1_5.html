LECTURE 01

Business Intelligence Concepts

What Is Business Intelligence?

Business Intelligence (BI) is using tools and techniques to turn raw data into useful decisions. A simple way to think about it: data goes in, insight comes out, and a manager makes a better choice.

🧠 Analogy

Think of BI like a GPS for a business. Raw data (like road sensors and maps) is collected constantly. The GPS (BI system) processes all of it and tells you: "Turn left — there's traffic on the highway." You don't need to know how the GPS works internally; you just need the right output at the right time to make a decision.

The Analytical Hierarchy — 5 Levels

Analytics moves from simple "what happened" questions to complex "what should we do" questions.

LevelQuestion It AnswersTimeReal Example
DescriptiveWhat happened?Past"We sold 500 units in March."
DiagnosticWhy did it happen?Past"Sales dropped because a competitor launched a cheaper product."
PredictiveWhat will happen?Future"Based on trends, we'll sell 480 units next March."
PrescriptiveWhat should we do about it?Future"Run a 10% discount campaign to push sales above 500."
ComparativeHow does X compare to Y?Any"Perth store vs Sydney store sales side by side."
💡 Quick Memory Trick

Think of it like a car accident:

  • Descriptive: "There was a crash on the freeway." (What?)
  • Diagnostic: "It happened because of wet roads and speeding." (Why?)
  • Predictive: "If it rains tonight, there's a 70% chance of another crash." (What next?)
  • Prescriptive: "Deploy speed cameras on wet roads to prevent it." (What to do?)
⚠️ Exam Trap

Predictive = "what WILL happen" (forecasting). Prescriptive = "what should we DO" (recommending action). Students often mix these two up. Predictive just tells you the future — prescriptive tells you how to change it.

LECTURE 02

Database Modelling

What Is a Database?

A database is organised, structured data stored consistently — like tables and lists, not free-form text. Think of it like a very powerful, shared spreadsheet that many people can use at once, with rules that keep the data valid.

🧠 Analogy — Library vs Pile of Books

A pile of books is data. A library is a database — books are catalogued, findable, categorised, and multiple people can use it simultaneously without chaos. A spreadsheet is like a personal bookshelf — fine for one person, but falls apart at scale.

Database vs Spreadsheet

FeatureSpreadsheetDatabase
Multiple users at once❌ One user at a time (usually)✅ Many simultaneous users
Large data performance❌ Slow with millions of rows✅ Designed for scale
Access control❌ Basic file permissions only✅ Fine-grained (user A sees table X, user B sees table Y)
Ease of use✅ Familiar, visual, easy❌ Requires SQL knowledge

Entities and Attributes

📌 Key Definitions
  • Entity: A "thing" we want to store data about (a Person, a Product, a Transaction)
    • Attribute/Property: A characteristic of an entity (Person's Name, Product's Price)
  • Row / Record: One specific instance (one particular person, one specific product)
  • Column / Field: One attribute (the "Name" column, the "Price" column)
💡 Example — A Person entity

The entity is: Person
The attributes are: FullName, EmailAddress, BirthDate
One row (record) might be: "Alice Smith", "alice@email.com", "1995-03-14"

Relationship Cardinalities

⚠️ Many-to-Many needs a linking table

You can't directly store a M:M relationship. You need a third "junction" table holding pairs of PKs. For Students ↔ Courses, you'd have an Enrolment table with (studentID, courseID) pairs.

ER Diagrams — Reading Them

An ER (Entity-Relationship) diagram is a visual map of your database design — showing entities (tables), their attributes (columns), and how they are related.

💡 Example — Transaction ↔ TransactionItem (from the lecture)

One Transaction can have many TransactionItems (e.g. one invoice with multiple line items). The FK transaction in TransactionItem points back to the Transaction it belongs to.

Database Design Steps (Memorise These)

  1. Define the entities — what "things" do we need to store? (People, Products, Orders...)
  2. Determine the tables — each entity usually becomes one table
  3. Identify Primary and Foreign Keys — how do rows uniquely identify themselves? How do tables link?
  4. Describe relationship cardinalities — is it 1:M, M:M, 1:1?
  5. Define all attributes — what columns does each table need?

ACID Principles

🧠 Analogy — ATM Cash Withdrawal

You withdraw $100 from an ATM. ACID guarantees that EITHER both happen (your account is debited AND cash dispensed) OR neither does. The bank balance can never be reduced without you getting the cash.

  • Atomicity: The whole withdrawal succeeds or nothing changes (no partial results)
  • Consistency: The bank database stays valid — you can't have a negative balance unless rules allow it
  • Isolation: Two people withdrawing simultaneously get correct results, as if they went one at a time
  • Durability: Once confirmed, the transaction is permanent — even if the power cuts out

💡 VARCHAR vs CHAR — When to use which?

Use VARCHAR for names, descriptions, emails — anything variable length.
Use CHAR for fixed codes like Australian state codes (NSW, VIC, QLD — always 2–3 chars) or postcodes (always 4 digits).

-- Good uses:
customerName VARCHAR(100),   -- names vary in length
stateCode    CHAR(3),        -- always "NSW", "VIC", "QLD"
postcode     CHAR(4)         -- always 4 digits in Australia

Creating a Database & Table — Full Example

💡 Step-by-step — Building a Customer table from scratch
-- Step 1: Create a database (do this once)
CREATE DATABASE 12345678_db;

-- Step 2: Tell MySQL to use that database (run at start of every session)
USE 12345678_db;

-- Step 3: Create a Customer table
CREATE TABLE 12345678_db.Customer (
  id          INT          NOT NULL AUTO_INCREMENT,
  fullName    VARCHAR(100) NOT NULL,
  email       VARCHAR(255) NOT NULL,
  birthDate   DATE,          -- nullable: not everyone shares their DOB
  isActive    BOOLEAN      DEFAULT 1,
  PRIMARY KEY (id)
);

Reading this column by column: id is a whole number, always required, auto-assigned. fullName is text up to 100 chars, always required. birthDate is optional (nullable). isActive defaults to 1 (true) if not specified.

ALTER TABLE — Modifying an Existing Table

💡 Example — Changing the Customer table after it's created
-- Forgot to add a phone number column? Add it now:
ALTER TABLE Customer ADD COLUMN phoneNumber VARCHAR(20);

-- "fullName" is confusing — rename it to "customerName":
ALTER TABLE Customer RENAME COLUMN fullName TO customerName;

-- Change phone to be mandatory (add NOT NULL):
ALTER TABLE Customer MODIFY COLUMN phoneNumber VARCHAR(20) NOT NULL;

-- Oops, phone number column is wrong — remove it entirely:
ALTER TABLE Customer DROP COLUMN phoneNumber;

INSERT, SELECT, UPDATE, DELETE — With Results

💡 INSERT — Adding rows
INSERT INTO Customer (fullName, email, birthDate) VALUES
  ('Alice Smith', 'alice@email.com', '1995-03-14'),
  ('Bob Jones',  'bob@email.com',   '1988-07-22');

Two rows inserted. MySQL auto-assigns id=1 to Alice, id=2 to Bob. isActive defaults to 1 for both.

💡 SELECT — Reading data
-- Get all columns from all rows:
SELECT * FROM Customer;

-- Get just names and emails:
SELECT fullName, email FROM Customer;

-- Get only active customers:
SELECT fullName, email FROM Customer WHERE isActive = 1;

💡 UPDATE — Changing existing data
-- Alice changed her email — update just her row:
UPDATE Customer
SET email = 'alice.smith@newemail.com'
WHERE id = 1;

-- Deactivate Bob:
UPDATE Customer SET isActive = 0 WHERE id = 2;
💡 DELETE — Removing rows
-- Delete only Bob (always use WHERE!):
DELETE FROM Customer WHERE id = 2;

-- DANGER: This deletes EVERY row in the table:
DELETE FROM Customer; -- ← NO WHERE CLAUSE = ALL GONE

-- DANGER: This deletes the whole table AND all its data:
DROP TABLE Customer;
⚠️ Most Dangerous Commands in SQL

DELETE FROM Table without WHERE → every row gone. DROP TABLE → entire table and data gone. Always run a SELECT first to preview exactly which rows would be affected before deleting.

More CRUD — Scripts, Generated Columns, Foreign Keys & WHERE

Running SQL Scripts

Instead of typing one command at a time, you write all your SQL in a .sql file and run the whole file at once. Commands run top-to-bottom. If one fails, everything stops at that line.

⚠️ Script Rules to Remember
  • Each command must end with a semicolon
  • Execution stops at the first error
  • Commands run instantly on the server — there's no "undo"
  • UniApps users: save scripts to OneDrive
  • Comment out (#) lines you've already run to avoid re-running them

Generated Columns

A generated column is calculated automatically from other columns. You never insert a value for it — the database works it out for you every time other values change.

🧠 Analogy

A spreadsheet formula like =B2*C2 in cell D2. You put values in B2 and C2, and D2 automatically shows the result. A generated column works the same way — you provide the ingredients (quantity, price), the database calculates the result (total).

💡 Example — TransactionItem with generated columns
CREATE TABLE TransactionItem (
  id          INT   NOT NULL AUTO_INCREMENT,
  description VARCHAR(255) NOT NULL,
  quantity    INT,
  unitPrice   FLOAT,
  hasGst      BOOLEAN    DEFAULT 0,
  totalPrice  FLOAT      GENERATED ALWAYS AS (unitPrice * quantity) STORED,
  taxAmount   FLOAT      GENERATED ALWAYS AS (hasGst * (unitPrice / 11)) STORED,
  PRIMARY KEY (id)
);

If you insert: description="Widget", quantity=5, unitPrice=20.00, hasGst=1

What MySQL stores (totalPrice and taxAmount auto-calculated)
iddescriptionquantityunitPricehasGsttotalPricetaxAmount
1Widget520.001100.001.82

You never insert values for totalPrice or taxAmount — they're calculated. Use DEFAULT for them when inserting: INSERT INTO TransactionItem VALUES (DEFAULT, "Widget", 5, 20.00, 1, DEFAULT, DEFAULT);

DEFAULT and CHECK Constraints

💡 Example — Adding safety rules to a table
-- 1. DEFAULT: if hasGst is not supplied, assume 0 (no tax)
ALTER TABLE TransactionItem MODIFY COLUMN hasGst BOOLEAN DEFAULT 0;

-- 2. CHECK: quantity must always be positive (can't sell -3 widgets)
ALTER TABLE TransactionItem ADD CONSTRAINT qCheck CHECK (quantity > 0);

-- 3. CHECK: price must be positive too
ALTER TABLE TransactionItem ADD CONSTRAINT priceCheck CHECK (unitPrice > 0);

-- Now try to insert an invalid row:
INSERT INTO TransactionItem (description, quantity, unitPrice) VALUES
  ('Bad Item', -5, 10.00);
-- ❌ ERROR: Check constraint 'qCheck' is violated.

CHECK constraints act like bouncers — they reject any data that breaks the rules before it enters the table.

Foreign Keys — Linking Tables

⚠️ Golden Rule

The parent table (the one being referenced) must exist first. You can't create a FK pointing to a table that doesn't exist yet. Create TransactionItem before Transaction if Transaction references TransactionItem.

💡 Example — Invoice references Customer
-- Create Customer FIRST (it's the parent)
CREATE TABLE Customer (
  id       INT          NOT NULL AUTO_INCREMENT,
  name     VARCHAR(100) NOT NULL,
  PRIMARY KEY (id)
);

-- THEN create Invoice (it's the child, references Customer)
CREATE TABLE Invoice (
  id         INT   NOT NULL AUTO_INCREMENT,
  customerID INT,
  amount     FLOAT,
  PRIMARY KEY (id),
  CONSTRAINT fk_cust FOREIGN KEY (customerID)
    REFERENCES Customer(id)
    ON DELETE CASCADE
);

Now if you try to insert an Invoice with customerID=99 but Customer id=99 doesn't exist — the database rejects it. This is referential integrity.

Referential Actions — What Happens When a Parent Row Is Deleted?

ActionEffectBest Used When…
CASCADEAlso deletes the child rows automaticallyChild rows are meaningless without the parent (e.g. delete order → delete order items)
SET NULLSets FK column to NULL in child rowsChild can still exist, just "unlinked" (e.g. delete employee → invoices stay, just have no assigned employee)
RESTRICTBlocks the deletion of the parent if children existYou must not delete a Customer who has active Invoices
💡 CASCADE vs RESTRICT — Which to choose?

Scenario: You want to delete Customer "Alice Smith" who has 3 Invoices.

  • CASCADE: Alice is deleted → her 3 invoices are also deleted automatically. ✅ Good if invoices are meaningless without a customer. ❌ Bad if you need to keep financial records.
  • RESTRICT: MySQL blocks the deletion and says "can't delete Alice, she has invoices." You must delete the invoices first. ✅ Good for protecting important financial data.

Indexes

🧠 Analogy — Book Index

Without an index, finding "chapter about cats" in a 500-page book means reading every page. With a book index, you flip to "Cats — page 247" instantly. Database indexes work the same way — they let MySQL jump directly to matching rows instead of scanning the entire table.

💡 Example — Adding an index to speed up email lookups
-- Users log in via email — this column gets searched constantly.
-- Adding an index makes those lookups much faster:
CREATE UNIQUE INDEX idx_email ON Customer(email);

-- Remove the index (doesn't affect the data or table):
DROP INDEX idx_email;

Trade-off: Indexes speed up reads but use extra storage and slightly slow down writes (INSERT/UPDATE) because the index must be updated too.

GROUP BY — Grouping & Summarising

🧠 Analogy — Sorting a pile of receipts

Imagine you have 100 receipts from different shops. You sort them into piles by shop name. Now for each pile (group), you can ask: "How many receipts in this pile?" (COUNT) or "What was the biggest purchase?" (MAX). That's exactly what GROUP BY does — it makes the piles, and aggregate functions answer questions about each pile.

SELECT → FROM → WHERE → GROUP BY → ORDER BY Mandatory order — getting this wrong = syntax error. WHERE always before GROUP BY. GROUP BY always before ORDER BY.
⚠️ The Most Important Rule in GROUP BY

In a GROUP BY query, your SELECT list may only contain:

  1. Columns listed in the GROUP BY clause
  2. Aggregate functions (AVG, MIN, MAX, SUM, COUNT)

Why? When 10 rows collapse into one group, any non-grouped column could have 10 different values — MySQL doesn't know which one to show, so it errors.

The 5 Aggregate Functions

💡 All 5 functions demonstrated on the TransactionItem table

Assume this is the TransactionItem table:

TransactionItem — source data
iddescriptionquantityunitPricehasGst
1Laptop2899.001
2Mouse525.000
3Keyboard375.000
4Monitor1450.001
 
SELECT
  hasGst,
  COUNT(id)        AS numItems,
  AVG(unitPrice)   AS avgPrice,
  MIN(unitPrice)   AS cheapest,
  MAX(unitPrice)   AS mostExpensive,
  SUM(unitPrice)   AS totalPrice
FROM TransactionItem
GROUP BY hasGst;
Result — one row per hasGst group
hasGstnumItemsavgPricecheapestmostExpensivetotalPrice
0 (no tax)250.0025.0075.00100.00
1 (has tax)2674.50450.00899.001349.00

The group hasGst=0 contains Mouse ($25) and Keyboard ($75). The group hasGst=1 contains Laptop ($899) and Monitor ($450). Notice hasGst appears in both SELECT and GROUP BY — so you can tell which result row belongs to which group.

⚠️ NULL Behaviour in Aggregation

All aggregate functions skip NULL values. Example: if a column has values [10, NULL, 20, NULL, 30], then:

  • COUNT(col) = 3 (counts only non-NULL)
  • COUNT(*) = 5 (counts all rows including NULLs)
  • SUM(col) = 60 (adds only the non-NULL values)
  • AVG(col) = 20 (60 ÷ 3, not 60 ÷ 5)

This can significantly affect your results when data has missing values!

Date Functions in Grouping

💡 Example — Sales grouped by month and year

Without date functions, grouping by date gives one group per exact date (too granular). Date functions let you group by just the month or year.

-- Count how many transactions happened in each month of each year
SELECT
  YEAR(date)  AS year,
  MONTH(date) AS month,
  COUNT(id)   AS numTransactions
FROM Transaction
GROUP BY YEAR(date), MONTH(date)
ORDER BY YEAR(date) ASC, MONTH(date) ASC;

Full Complex Query — All Clauses Together

💡 The Lecture's Most Complex Example — Broken Down
SELECT
  department,
  MONTH(date),
  YEAR(date),
  COUNT(id)        AS numSales,
  MIN(salePrice)   AS cheapestSale
FROM ExampleTable
WHERE department LIKE 'SALES %'
GROUP BY department, MONTH(date), YEAR(date)
ORDER BY MIN(salePrice) DESC;

Step by step — what MySQL does internally:

  1. FROM ExampleTable — load all rows from the table
  2. WHERE department LIKE 'SALES %' — filter: only keep rows where department starts with "SALES ". This happens BEFORE grouping.
  3. GROUP BY department, MONTH(date), YEAR(date) — group remaining rows. Every unique combination of (department, month, year) becomes one result row. If SALES-NORTH sold in Jan 2023 and Feb 2023, those are two separate groups.
  4. SELECT — calculate aggregates for each group: COUNT(id) = how many sales, MIN(salePrice) = cheapest sale price in that group.
  5. ORDER BY MIN(salePrice) DESC — sort the result groups: the group with the highest minimum sale price appears first.

AS Aliases, WITH ROLLUP

💡 WITH ROLLUP — Adding a grand total row
SELECT YEAR(date) AS yr, SUM(amount) AS totalSales
FROM Invoice
GROUP BY YEAR(date) WITH ROLLUP;
Result — note the NULL row at the bottom = grand total
yrtotalSales
2022$5,200.00
2023$8,750.00
NULL$13,950.00 ← grand total for ALL years

The NULL in the yr column of the last row means "this is not one specific year — this is ALL years combined." It's the grand total row added by WITH ROLLUP.
